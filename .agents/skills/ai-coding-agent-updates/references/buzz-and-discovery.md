# バズ判定と対象外ツール探索

## 原則

公式情報と人気シグナルを別レイヤーで扱う。製品の機能、提供条件、日付は公式情報源で確認し、コミュニティ投稿は反応の観測にだけ使う。

## バズの情報源

優先順:

1. 公式GitHub Release、Discussion、Issue、Pull Requestのreactionsやcomments
2. Hacker Newsのpointsとcomments
3. Redditのscoreとcomments
4. ベンダー公式投稿に対する公開reactions、reposts、comments
5. 複数の独立した技術コミュニティや開発者による具体的な検証

検索結果順位、検索結果件数、転載記事数、フォロワー数だけでは判定しない。取得時点で変化する数値には観測日時を付ける。

## 判定

### confirmed

次をすべて満たす。

- 対象期間内の公式更新をanchorにできる
- 独立した2つ以上のコミュニティsourceがある
- 少なくとも1つはpoints、comments、reactions、star増加などの測定可能な反応を示せる
- 反応が機能そのものに向けられたものだと確認できる

### emerging

次のどちらかを満たす。

- 測定可能な反応が1つあり、通常より注目されたと判断できる比較材料がある
- 独立した2つ以上の具体的な検証や議論があるが、比較可能な数値を取得できない

### 該当なし

- 単一投稿しかない
- 数値は大きいが製品全体への反応で、対象更新との関係を確認できない
- 宣伝投稿や転載が中心
- 根拠を再確認できない

週次レポートは `confirmed` を優先し、`emerging` を含めても合計3件までとする。

## 有望ツールの探索

月次だけで行い、対象ツール一覧に含まれないAIコーディングエージェントを探す。一般チャット、モデル単体、コード補完だけの製品、更新停止プロジェクトは除外する。

候補の製品事実は、公式サイト、公式Docs、公式Changelog、公式OrganizationのRepositoryで確認する。

次のうち2項目以上を満たすものだけ掲載する。

- 対象月に意味のある公式リリースがある
- 過去90日に継続的な公式更新がある
- 対象ツールにない明確な機能差がある
- 公開repositoryで継続的な開発と利用反応を確認できる
- 独立した複数のコミュニティで具体的な利用報告がある
- 企業利用に必要な権限、監査、分離実行などの仕組みが公式に示されている

## 候補ごとの記録

- 正式名称
- 公式URL
- 提供主体
- 対象surface（CLI、IDE、cloud、reviewなど）
- 対象月の公式更新
- 提供段階
- 有望性を支える事実
- 有望と判断した推論
- 制約または不確実性
- 翌月に確認するシグナル

基準を満たす候補がなければ、理由を短く添えて「なし」とする。件数を埋めるために候補を追加しない。
