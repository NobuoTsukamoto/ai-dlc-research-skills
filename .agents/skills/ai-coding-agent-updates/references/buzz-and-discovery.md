# 公式イベントと対象外ツール探索

## 公式イベントの判定

日次の既存収集候補から次の条件をすべて満たす告知を選ぶ。イベントのための追加巡回やコミュニティ反応の収集は行わない。

- 既存の公式情報源に含まれる、主催者または対象製品の提供主体による公式告知である。
- 対象のAIコーディング製品またはAIを用いたソフトウェア開発に直接関連する。
- イベント名と開催日または開催期間を確認できる。場所・オンライン形式、タイムゾーン、参加条件は明記されたものだけ記録し、不明なら「不明」とする。
- 新規開催告知または開催日・期間の変更を、実際の告知日または変更日とともに確認できる。対象日より前の告知や変更でも、今回の収集で初めて確認した候補は遅延発見として記録する。

告知日・変更日と開催日、発見日を別に扱う。発見日はAsia/Tokyoで実際に確認した日とし、日次の対象日とは区別する。集計期間は発見日ではなく告知日・変更日で判定する。日付を確認できない場合は推測で補わず、理由と公式URLを発見時の日次の確認不能に記録する。古い公開日のページが更新されても変更日を確認できなければ、新着の日程変更と断定しない。

日次ではイベント名、関連製品または開発との関連、告知日・変更日、発見日、開催日時・タイムゾーン、開催形式・場所、変更内容、公式URLを記録する。変更前の日程が不明なら「不明」とする。1つの記事に製品更新とイベントが含まれる場合、それぞれの欄に記録するが、イベント単独の告知は製品更新ログへ追加しない。

遅延発見時は、発見時の対象日の日次に記録し、告知日・変更日に対応する日次が既にあればそのイベント欄にも追記する。その日次が欠落している場合は作成せず、発見時の日次に欠落を記す。告知日・変更日を含むISO週の週次と暦月の月次が既にあれば、それぞれのイベント欄に追記する。まだ存在しないレポートは新規作成せず、後の週次・月次作成時に発見時の日次から取り込む。既存の本文や確認不能・coverageを消さず、更新箇所に発見日と補完した事実を残す。追記できない場合は実行を失敗させ、収集状態を確定しない。

同一イベントは主催者、名称、開催回を照合し、異なるURLの告知や同じURLの更新も1件に統合する。日程変更は元の告知と区別して日付、変更前後、出典を残す。再実行時は既存レポートを維持し、同じ告知・変更を重複追加しない。週次・月次では対象期間内の日次に加え、期間後の保存済み日次の公式イベント欄も確認し、告知日・変更日が対象期間内の遅延発見を取り込む。月次は週次も参照し、週境界をまたぐ項目を日付で振り分ける。

対象となる既存情報源を確認できた範囲で該当がなければ「確認した情報源に該当なし」とする。取得不能、日次・週次の欠落、旧形式でイベント欄がない場合、または候補の判定に必要な情報が不明な場合は、該当の情報源・日付と理由を「確認不能」に記し、coverageを `partial` とする。該当イベントを確認できても、この確認不能は消さない。

既存情報源に掲載されないイベントは検出できず、網羅的な調査ではない。必要に応じて人間が手動で確認する。

## 有望ツールの探索

月次だけで行い、対象ツール一覧に含まれないAIコーディングエージェントを探す。一般チャット、モデル単体、コード補完だけの製品、更新停止プロジェクトは除外する。

バズ調査とは別に、既存の公式情報源に現れた候補だけを検討する。自動実行では新しい情報源を巡回せず、存在と機能を既存の公式情報源で確認できない候補は掲載しない。対象外ツールの探索も網羅的ではない。

次のうち2項目以上を満たすものだけ掲載する。

- 対象月に意味のある公式リリースがある
- 過去90日に継続的な公式更新がある
- 対象ツールにない明確な機能差がある
- 公式情報源に継続的な開発が示されている
- 企業利用に必要な権限、監査、分離実行などの仕組みが公式に示されている

## 候補ごとの記録

- 正式名称
- 公式URL
- 提供主体
- 対象surface（CLI、IDE、cloud、reviewなど）
- 対象月の公式更新
- 提供段階
- 有望性を支える事実
- 有望と判断した推論
- 制約または不確実性
- 翌月に確認するシグナル

基準を満たす候補がなければ、理由を短く添えて「なし」とする。件数を埋めるために候補を追加しない。
